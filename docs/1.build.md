# Build and assets

> How the Vite pipeline turns `src/` and `public/` into a deployable `dist/`, including the generated service worker and build id.

## Entry points

[`index.html`](../index.html) is the only HTML entry point. It links the stylesheet from `/src/style.css`, loads `/src/main.js` as an ES module, and keeps three small inline bootstrap scripts:

- the service-worker unregister guard, which also handles `?reset`;
- a window `error` safety net that replaces the panel with a failure message;
- a greeting alert.

[`src/main.js`](../src/main.js) boots the app. It fetches `trips/olympic/trip.json` (served from `public/trips/olympic/trip.json`), replaces the panel with a readable error if the fetch fails, and calls `start(trip)` from [`src/app.js`](../src/app.js). The service worker is registered only in production builds (`import.meta.env.PROD`), so the dev server never installs one.

[`src/app.js`](../src/app.js) exports `start(TRIP)` and contains the map and panel logic. Four functions used by inline `onclick` attributes in generated markup — `goTo`, `loadElev`, `saveElev` and `show` — are assigned to `window` explicitly at the end of the module.

[`src/style.css`](../src/style.css) is the whole stylesheet. Its first line is `@import 'leaflet/dist/leaflet.css'`, which keeps the cascade order the previous inline stylesheet relied on.

## Source, verbatim and output

| Location | Role |
| --- | --- |
| `src/` | Processed source. JavaScript modules are bundled and the stylesheet is processed; output filenames get content hashes under `dist/assets/`. |
| `public/` | Copied verbatim to `dist/`. Reserved for files that need exact, stable URLs: PWA icons, `logo.svg`, `manifest.json`, `sw.js`, `trips/olympic/trip.json` and `reset.html`. |
| `dist/` | Generated output. Never edit by hand; rebuild instead. Not committed. |

Leaflet 1.9.4 is an npm dependency (`dependencies` in `package.json`) and is bundled with the app rather than vendored under `public/`. Vite hashes Leaflet's sprite images and inlines any asset under 4 KB as a data URI.

The [trip format](2.trip-format.md) page lives under `docs/`, not `public/`, so developer documentation is neither published nor precached.

## Build id

[`vite.config.js`](../vite.config.js) runs a `closeBundle` plugin that computes an 8-character build id from SHA-256 over the build inputs: `index.html`, `vite.config.js`, `src/**` and `public/**`. The id is:

- injected as `__BUILD_ID__` and shown in the app's panel footer (`dev` during development);
- written to `dist/build.json` as `{ "id": ..., "files": [...] }`;
- used as the app-cache name `hdl-app-<id>` in `dist/sw.js`.

Because the id is derived from content, there is no manual version bump and no `?v=` query string. Any change to the app, its configuration or `public/` — including the trip file — produces a new id and a new cache.

## Generated service worker

[`public/sw.js`](../public/sw.js) is a template with two placeholders: `__CACHE_NAME__` and `__PRECACHE__`. After Vite writes `dist/`, the plugin:

1. walks the emitted files and builds the precache list — every file except `sw.js`, `build.json` and source maps;
2. puts the scope root `./` first so a cold install can serve the app shell;
3. replaces the placeholders with the build id and the list, then writes `dist/build.json`.

The list has to be generated: Vite's content-hashed filenames change on every build, so a hand-written list or version constant would go stale and break offline loads. The build fails if a listed file is missing or either token is absent; `npm run check:build` fails if a placeholder survives anywhere in `dist/`.

The app-cache lookup uses `ignoreVary: true`. Vite emits `crossorigin` on its assets and the server sends `Vary: Origin`, which otherwise makes a cached hashed asset miss on a cold offline load. Map tiles use a separate `hdl-tiles-v1` cache that is not tied to the build id, so saved tiles survive app updates.

## Verifying a build

`npm run check:build` ([`scripts/check-build.mjs`](../scripts/check-build.mjs)) cross-checks `dist/build.json` and `dist/` in both directions, confirms that `dist/sw.js` contains the matching cache name and precache array, rejects unresolved placeholders, and verifies that `dist/index.html` references only assets that exist. It also fails if built files still contain `/src/`, `lib/leaflet` or `?v=` references.

`npm run test:build` builds the site, runs the check, then runs Playwright against `dist/` on port 11101 using [`playwright.build.config.js`](../playwright.build.config.js). The build suite covers a production asset load with no missing files, a cold offline service-worker load, and a safe online reload with a single app cache; it also re-runs the smoke spec against the same visual baselines as the dev suite.

## Diagnostics

[`public/reset.html`](../public/reset.html) is the "App check" page, served at `reset.html`. It reads `build.json`, fetches every precached file plus `sw.js` with `cache: "no-store"`, and prints the build id and a `Checked N files, M failed — OK` (or `FAILED`) summary. It also reports registered service workers, saved caches, and whether the elevation, tile and water services are reachable.

The page's button unregisters the service worker, deletes `hdl-*` caches, clears the app's saved localStorage keys and reopens the app. Opening the app with `?reset` performs the same cleanup through the inline guard in `index.html`.

## Visual baselines

Playwright snapshots live in [`docs/screenshots/`](screenshots/) and are shared by the dev and build configs through `snapshotPathTemplate`. The projects cover desktop landscape, tablet portrait and mobile portrait viewports. Baselines are platform-specific, so CI and the Pages deployment run the unit and build steps only; refresh them locally with `npm run test:e2e:update` after an intentional UI change.
